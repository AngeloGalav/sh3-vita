# Porting Silent Hill 3 to PS Vita — feasibility study and plan

Study of November 11, 2026, on the current work machine (`agala-ai-linux@10.0.0.225`),
from the `sh3-vita` repository (qualified SH4 port) and the `Silent Hill 3/` support placed at
the root. Mission given by Valentin: **port SH3 to Vita building on the SH4 port's code**.

Convention of this document: **verified** = measured or read here, with the command; **inferred** =
reasoning from verified facts; **unknown** = to be lifted. Nothing here announces a functional port,
a performance or a hardware validation.

## 1. Provided support

Verified (`ls`, `file`, `objdump`, SHA-256):

- `Silent Hill 3/` — 4.9 GB, unversioned. 2003 PC release (`deviance.nfo`, `sh3.exe` dated
  2003-09-03) **plus** a modern "Silent Hill 3 PC Fix" patcher (`Silent_Hill_3_PC_Fix.dll`,
  a 2024 `d3d8.dll` that relays to `d3d9on12.dll`, `dxbcSigner.dll`, `SH3Config.exe`,
  `SH3FileValidator.exe`).
- Scope decision: the port uses **neither the patcher nor its D3D wrapper**, as for SH4 where the
  port's runtime itself provides Direct3D 8, DirectInput 8 and DirectSound.
  The patcher must not be redistributed (third-party licence, see §10).
- `sh3.exe` — PE32 i386, 3,338,240 bytes, SHA-256
  `8ff8f74806f55843b9bc277508b17c8926999f292c65dbe7949325087d460918`, not packed.
  Image base `0x400000`; sections `.text` `0x401000` (size `0x289000`), `.rdata` `0x68a000`,
  `.data` `0x6b0000` (`0x7c000`), `.data1` `0x717a000`, `.rsrc` `0x717b000`.
- Working copy placed in `game/sh3.exe` (directory ignored by Git, as for SH4).

## 2. Windows API surface: the SH4 shim is directly transposable

Verified (`python3 re/pe_imports.py game/sh3.exe`, to compare with `re/LEDGER.md` for SH4):

| DLL | SH3 | SH4 (LEDGER) | Gap for the port |
|---|---|---|---|
| KERNEL32 | 144 | 97 | delta to add (GDI/resources, `MapViewOfFile`, `SetThreadAffinityMask`, `PulseEvent`…) |
| USER32 | 54 | 26 | + `ChangeDisplaySettingsA`, `RegisterDeviceNotificationA`, cursors, `DrawTextW` |
| GDI32 | 11 | 1 | **new**: fonts (`CreateFontIndirectA`), `CreateDIBSection`, `DrawText*` |
| WINMM | 16 | timers | + `mmio*` (WAV/RIFF reading by the game) |
| DSOUND | `#11` (DirectSoundCreate8) | idem | reusable |
| DINPUT8 | `DirectInput8Create` | idem | reusable |
| d3d8 | `Direct3DCreate8` | idem | reusable |
| ole32 / OLEAUT32 | 6 / 2 | 6 / – | `CoTaskMemAlloc/Free` already covered |
| ADVAPI32 | 4 (registry) | idem | reusable |
| IMM32 | 2 | 2 | reusable |

No DirectShow, no Bink: all the video and audio decoding is **statically linked into
`sh3.exe`** (see §4). Consequence: the shim `port/src/win32`, `port/src/dx`, `port/src/d3d8`
(≈ 9,400 lines) remains the right base; the delta is a list of imports to implement, not an
overhaul.

## 3. Instruction set: x87 like SH4, SIMD concentrated in the codecs

Verified (`objdump -d --no-show-raw-insn` census + Capstone decoding of the 8,145 functions
exported by Ghidra 12.1.4, `re/out/functions-sh3.json`, 532,994 body instructions):

- **x87 dominant**, like SH4: `flds` 23,904, `fstps` 18,839, `fmuls` 10,806, `fsubs` 6,610,
  `fadds` 5,915, `fnstsw` 6,229. The recompilation's x87 model (stack of 8 reals, static
  register) applies with no change of concept.
- **SIMD: 5,759 instructions out of 532,994 (1.1%), in 43 functions out of 7,958.**
  Distribution per 64 KiB block: `0x650000` → 4,155, `0x660000` → 1,510, `0x640000` → 61,
  `0x630000` → 33. **Outside the range `0x650000`–`0x670000`: 5 functions, 94 instructions**
  (`0x6321d3` 32, `0x64fb36` 29, `0x64cb70` 20, `0x64cb30` 12, `0x63b480` 1).
- SIMD mnemonics: `movq` 1701, `pfmul` 813, `pfadd` 488, `punpckhdq` 424, `punpckldq` 327,
  `movd` 264, `pxor` 93, `pmaddwd` 93, `psrlq` 92, `paddd` 86, `psrad` 80, `paddw` 75,
  `pfsub` 68, `psubw` 62, `movaps` 56, `movlpd` 53, `femms` 51, `pand` 46, plus supplementary
  SSE1/SSE2 (`mulps` 441, `shufps` 367, `movss` 282, `addps` 270 on the full `.text` side).
  This MMX + 3DNow! + `pmaddwd`/`punpck*l*dq` mix is the signature of a **video-codec IDCT**.
- The recompilation `recomp/x86rec.py` currently emits `rt_unimpl()` — therefore a fatal stop —
  on **every** SIMD instruction (`is_simd`, line 494; emission line 792). SH4 did not need it on
  the executed paths; SH3 does need it, but almost only in the codec range.

**Strategic consequence (inferred, strong)**: one must not "implement SSE for all of SH3".
One must (a) translate the ~94 instructions outside the codec, (b) **replace the codec range with
native code**, as the SH4 port did for its MPEG-1 reader (`pl_mpeg` + Layer I decoder written
in `port/src/dx/movie.c`). This removes 98% of the SIMD problem and avoids recompiling an x86 IDCT
on a Cortex-A9.

## 4. Codecs: CRI fingerprints

Verified (`strings -a -n 5 game/sh3.exe`): `ADXF/PC Ver.7.09 Build:Jun 26 2003 17:14:31`,
`ADXPC(PRO) Ver.1.10`, `ADXT/PC Ver.8.88c`, `(c)CRI`, `ADXF_ERR_*`, `adxFileOpen()`, and archive
names `amcm.afs`, `bc.afs`, `br2f.afs`, `bu1f.afs`, `cc.afs`, `cr.afs`.

Inferred: **CRI ADX** audio (ADX PC 2003 library) and, very probably, **CRI Sofdec** video —
both statically linked, in the SIMD range identified in §3. To confirm by reading the film-opening
function (next targeted RE work).

## 5. Game data

Verified:

- `data/` = 34 `.arc` archives (4.9 GB) + `data/movie/` (7 `.000` files, 462 MB) +
  `data/pic/*.bmp`.
- `.arc` **not encrypted**: 16-byte header (magic `07 05 03 20`, entry count, table size),
  then 16-byte records (offset, size, …). Example `msg.arc`:
  371 entries, the first at offset 7512, size 13906.
- `arc.arc` is a **gzip** (90,016 bytes decompressed) containing the engine's **path table of
  logical paths**: `data/eff_tex/flame003_tr.pic`, `data/eff_tex/flame032.tbn2`,
  `data/eff_tex/fire_tex.psd`, … The engine therefore opens virtualized paths; the `.arc`
  are the containers. This is the entry point of a data preparer.
- `.000` films: entropy ≈ random (index of coincidence 0.00391), no short XOR key detected
  (IC per class stable up to period 256), but identical 4-byte blocks spaced 4096 bytes
  apart starting at `0x8000` → **container by 4096-byte sectors**.
  This is not Bink (SH2 PC used `BIKi`, present in `../sh2-vita`) nor SH4's MPEG-1.
  Unknown: exact format and header (encrypted?).

## 6. What is reusable from the SH4 port, measured

| Element | Size | Reusability for SH3 |
|---|---|---|
| `recomp/x86rec.py` | 1,327 l. | base of the recompilation; the 14 `WRAPS` and some addresses (`0x4287f0`, `0x404a00`…) are SH4 → to make optional per target |
| `port/src/d3d8/` | 5,775 l. | D3D8 → vitaGL emulation, 1.x shader translator, program cache: reusable, to realign on SH3's actual calls |
| `port/src/dx/` | 2,315 l. | DirectInput/DirectSound reusable; `movie.c` (MPEG-1 + Layer I) **SH4-specific** → to replace (§5, §4) |
| `port/src/win32/` | 1,369 l. | reusable core + import delta (§2) |
| `port/src/rt/` | 4,035 l. | guest runtime (`x86rt`), heaps, log: reusable; `collision_*`, `model_uv`, `sound_archive`, `audio_adpcm`, `cinematic`, `audit`, `options`, `controls_help` = **SH4 knowledge** (≈ 350 hard-coded addresses in total, concentrated here) |
| `port/src/vita/` | 920 l. | startup, memory, life cycle: reusable |
| benches and tools | `port/test/`, `tools/` | method (PC reference, captures, audits) transposable; the Vita drivers are SH4 |

The emulation core is therefore **not** coupled to the game's addresses: the coupling is concentrated
in the SH4 optimization/qualification modules, which will stay disabled for SH3 at the start.

## 8. Compilation container (request of November 11)

Added in `docker/`:

- `vita-sdk.Dockerfile` — base `vitasdk/vitasdk:latest`, then **vitaGL recompiled at revision
  `2bdbe895ddc6a7e410a9ea55a8f53d8173c61ad8`** (the one of the repository's patches) with
  `NO_DEBUG=1 STORE_DEPTH_STENCIL=1`, patch `vitagl-shared-depth.patch` applied, and a final
  check of the two depth-retention modes (the guard of `port/build.sh`).
- `build-vita.sh` — builds the image on demand, then runs `port/build.sh` in the container,
  with a Docker volume for the CMake folder (incremental rebuilds). Deposits the VPK in `build/`.
- `smoke.sh` — **validates the chain without game code**: compiles a minimal vitaGL application
  (60 frames, red background) and packages it into `build/smoke.vpk`. Useful as long as `port/gen/`
  does not exist.
- `README.md` — usage.

What the container guarantees: toolchain, patched vitaGL, vitashark, ShaccCg, VPK packaging.
What it does not guarantee: that the game compiles (requires `port/gen/`), nor that it runs.

## 9. Proposed milestones

Each milestone has an observable criterion; none promises 30 frames/s nor a console validation.

| Milestone | Work | Criterion before moving to the next |
|---|---|---|
| **J0 — Target tooling** | Parameterize `x86rec.py` per target (`sh4` by default, `sh3` explicit), output `port/gen-sh3/`, SH3 import list, Docker image + `smoke.vpk`; set up the separate SH3 repository (decision §11) | the C of `sh3.exe` is generated without error; `docker/smoke.sh` green |
| **J1 — SIMD outside the codec** | Translate the ~94 instructions of the 5 concerned functions (SSE1/SSE2/MMX per census), differential benches against the original | zero `rt_unimpl` outside the codec range on a reference run; exact benches |
| **J2 — Linked startup** | Missing imports, entry point, threads, registry/config, file path | the executable reaches the title screen (emulator or PC) with the real data |
| **J3 — Data** | `.arc` reader/preparer + `arc.arc` table, `.pic` textures, models, ADX sounds | one real room rendered and compared |
| **J4 — Rendering** | Census of the D3D8 methods and shaders actually called by SH3, then adaptation of the translator | set of scenes compared image by image, gaps classified |
| **J5 — Audio and films** | Native decoders for ADX and for the film format (after identification), replacing the codec range | FMVs played and full audio without recompiling the SIMD range |
| **J6 — Real console** | VPK, guest memory budget to re-measure for SH3, controls, save, sleep/wake | a Vita that starts and plays, evidence and fingerprints recorded |

Recommended order: J0 → J1 → J2, in parallel J3 (the data does not depend on the SIMD).

## 10. Assumed risks and limits

- **Memory**: SH4 fits in 200 MB of guest with strong constraints (host heap 24 MB,
  vitaGL 32 MB). SH3's budget (BSS, the game's heap, resident CRI archives) is **not measured**.
  This is the risk n°1 of a Vita port, not the rendering.
- **Undocumented formats**: `.arc`, `.pic`, `.tbn2`, models, `.000` films. Each requires an RE
  phase; nothing obliges the first day to suffice.
- **Shaders**: the SH4 translator covers vs/ps 1.x. SH3 perhaps uses other profiles
  (census J4). A non-covered profile = a missing pass, not a silent crash.
- **No console here**: without a reachable Vita, no real measurement is possible; the emulator
  proves neither the real GPU nor the real memory. Accepted for now by the decision of §11:
  the bench is Vita3K + PC, and a physical Vita may be used later.
- **Licence and distribution**: the data stays the player's; the "SH3 PC Fix" patcher
  and its DLLs are not redistributable; the generated C stays a derived work of the binary (never
  versioned, as for SH4).
- **This document validates nothing**: neither performance, nor stability, nor parity with the original.

## 11. Decisions resolved with Valentin — November 11, 2026

The four questions of this section were decided by Valentin on November 11, 2026:

1. **Console**: for now, no physical Vita is needed. Work proceeds on the emulated bench
   (Vita3K+) + PC. A physical Vita may be used later.
2. **Tree**: SH3 lives in a **separate repository**, not as a `sh3` target inside this SH4 repository.
   J0 includes setting up that repository.
3. **Comparison reference**: the release in the provided folder is the oracle. **No Steam/GOG
   release of SH3 exists**; the 2003 release with `sh3.exe` SHA-256
   `8ff8f74806f55843b9bc277508b17c8926999f292c65dbe7949325087d460918` is the sole reference for
   images and formats.
4. **First lot**: start with **J0** (target tooling), then J1/J2 with J3 in parallel.

Additional latitude granted by Valentin: **texture quality may be reduced if needed** (memory or
cadence trade-off), as long as the result is measured and documented rather than assumed.
